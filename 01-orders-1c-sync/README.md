# Сверка заказов маркетплейса с выгрузкой 1С

Небольшой PHP-модуль, который берёт заказы маркетплейса (в формате эмуляции API),
сверяет их с выгрузкой номенклатуры из 1С и формирует  отчёт:
какие позиции нельзя отгружать и почему. Параллельно — исправленный
`bugs/OrderTotal.php` с разбором ошибок.

---

## 1. Быстрый старт


```powershell
# из папки проекта (там, где лежит docker-compose.yml)
docker compose up --build
```

После прогона:

- в `./reports/` появятся `report.html` и `report.csv`;
- в `./logs/` — `sync.log` с предупреждениями и ошибками обработки;
- в консоль выведется сводка и построчный разбор каждого заказа.

Чтобы запустить самопроверку `OrderTotal.php`:

```powershell
docker compose run --rm sync php bugs/OrderTotal.php
```

Ожидаемый вывод — `[OK  ]` по всем кейсам и фраза «Все проверки пройдены».

### Несколько команд в одной сессии

```powershell
# подробный режим: лог дублируется в stderr
docker compose run --rm sync php bin/sync.php --verbose

# прогон со своими путями
docker compose run --rm sync php bin/sync.php --orders=/app/data/orders.json --nomenclature=/app/data/nomenclature_1c.csv
```

## 3. Что делает скрипт

1. **`NomenclatureLoader`** читает CSV из 1С. Формат выгрузки:
   - UTF-8 с BOM, разделитель `;`, запятая как десятичный разделитель,
     пробел как разделитель тысяч (`1 250,00` = 1250.00), перевод строк CRLF.
   - Битые строки пишутся в лог, загрузка не падает.
2. **`OrderLoader`** читает `orders.json`. Чтобы переключиться на реальный API
   маркетплейса, достаточно заменить `fromFile()` на `fromUrl()` (или любой
   HTTP-клиент) — парсер JSON тот же.
3. **`Matcher`** построчно сверяет каждый заказ:
   - нормализует артикулы (`trim` + `uppercase`);
   - проверяет наличие SKU в 1С;
   - сравнивает цену в заказе и в 1С (с допуском 0.01 BYN);
   - контролирует остаток **кумулятивно**: заказы обрабатываются по `created_at`,
     каждый «настоящий» заказ уменьшает виртуальный остаток;
   - детектит дубли заказа (повторяющийся ID), дубли позиций внутри заказа,
     пустые заказы, заказы без `total` и без цены.
4. **`Report`** рендерит вывод в трёх форматах сразу: консоль, CSV, HTML.
5. **`Logger`** пишет всё, что не поместилось в отчёт, в `logs/sync.log`.

## 4. Какие расхождения ищет

| Тип | Уровень | Что значит для менеджера |
|---|---|---|
| `sku_not_found` | error | Артикула нет в 1С — позицию нельзя завести в учётную систему, нужно либо добавить номенклатуру, либо отказать клиенту. |
| `price_mismatch` | error | Цена в заказе отличается от цены в 1С. Нужно согласовать с маркетплейсом или скорректировать в 1С. |
| `stock_short` | error | Не хватает остатка с учётом уже принятых к отгрузке заказов. Нужно либо докупить, либо предлагать покупателю замену. |
| `duplicate_order` | error | ID заказа встречается дважды. В отгрузку идёт только первый экземпляр. |
| `duplicate_item` | warn | Один и тот же SKU в нескольких строках одного заказа — обычно это ошибка выгрузки, лучше объединить. |
| `empty_order` | warn | Заказ без позиций — проверить выгрузку. |
| `null_total` | warn | У заказа нет суммы — нельзя передать в 1С без ручной правки. |
| `no_price` | error | У позиции нет цены — то же. |
| `bad_qty` | warn | Некорректное количество (<= 0). |
| `total_mismatch` | warn | Сумма позиций не сходится с `total` в заказе. |
| `cancelled` | info | Заказ отменён — в отгрузку не идёт, остаток не расходует. |

Также в лог пишется отдельное предупреждение, если **в самой 1С один и тот же
артикул представлен несколькими карточками** (в тестовых данных такое есть у
`TS-1017`). Используется первая встреченная карточка — это безопаснее, чем
схлопывать разные цены и остатки.

## 5. Принятые решения (то, что не описано в задании явно)

### Что считается дублём заказа

**Повторяющийся `id` в `data.orders`.** Обрабатываем в порядке `created_at` —
первое вхождение «настоящее» (расходует остаток, идёт в отчёт как обычно),
последующие помечаются как дубль и остаток **не расходуют**. Это исключает
случайную двойную отгрузку, если маркетплейс прислал ту же страницу ещё раз.

> Если у вас в задаче смысл «дубль позиции в заказе» — это другое. Для этого есть
> отдельная проверка `duplicate_item`: один и тот же SKU в нескольких строках
> одного заказа. Такие строки не объединяем автоматически (менеджер должен решить),
> но остаток считаем по сумме.

### Что делаем с отменёнными заказами

`status = "cancelled"` → заказ участвует в отчёте (чтобы менеджер его видел), но:
- помечается тегом `[ОТМ]`;
- не расходует остаток;
- всё равно сверяется цена (для диагностики — вдруг цена отличалась, и это
  выяснится, когда покупатель перезакажет).

### Считаем ли остаток по каждому заказу отдельно или суммарно

**Суммарно, в порядке `created_at`.** Это ближе к жизни: если два заказа
забирают один и тот же остаток, первому хватает, второму — нет. В тестовых
данных такой кейс есть: `TS-1025` — сток 4 шт., заказы `MP-24013` (нужно 3)
и `MP-24021` (нужно 2). Первый проходит, второй помечается `stock_short`.

Для отладочного режима также показывается исходный остаток (`stock_total`)
и доступный к моменту обработки (`stock_left`) — удобно показать менеджеру,
что «на моменте отгрузки оставалось N шт.», а не только дефицит.

### Нормализация артикулов

`trim` + `strtoupper`. В тестовых данных встречается `" ts-1002"` (с пробелом
и в нижнем регистре). Без нормализации это был бы отдельный «новый» SKU,
которого нет в 1С — ложное срабатывание. Нормализация устойчива к типичным
ошибкам маркетплейса.

### Толерантность к ценам

Разница ≤ 0.01 BYN считается совпадением (защита от ошибок округления float).
Для настоящих расхождений в отчёт пишется и цена заказа, и цена 1С.

### Битые данные в номенклатуре

Если строка не парсится (не 6 колонок, не число в цене/остатке, пустой
артикул) — пишется в лог, скрипт идёт дальше. Это сознательно: одна битая
строка не должна валить весь обмен.

## 7. Аргументы CLI

```text
--orders=<путь>       путь к файлу заказов (по умолчанию data/orders.json)
--nomenclature=<путь> путь к CSV номенклатуры (по умолчанию data/nomenclature_1c.csv)
--out=<каталог>       куда складывать отчёты (по умолчанию reports)
--log=<путь>          путь к лог-файлу (по умолчанию logs/sync.log)
--verbose             дублировать лог в stderr
```

Код возврата:
- `0` — ошибок в заказах нет;
- `2` — есть хотя бы одна ошибка ;
- `1` — фатальная ошибка (не нашли файл, не распарсился JSON и т. п.).

  - `MP-24008` (`TS-1012`: нужно 7, в 1С — 5);
  - `MP-24016` (`TS-1033`: нужно 1, в 1С — 0);
  - `MP-24017` (`TS-1006`: суммарно нужно 3 — две строки в одном заказе, в 1С — 2);
  - `MP-24021` (`TS-1025`: нужно 2, но `MP-24013` уже забрал 3 из 4).
- **Дубль заказа**: `MP-24009` (два идентичных экземпляра). В отгрузку идёт первый.
- **Дубль позиции в заказе**: `MP-24017` (`TS-1006` в двух строках).
- **Заказ без позиций**: `MP-24028`.

- **Несовпадение суммы**: `MP-24025` (сумма позиций 98.20 BYN ≠ `total` 103.20 BYN —
  несоответствие в самих данных маркетплейса).
- **SKU с пробелом и в нижнем регистре**: `MP-24022` (` ts-1002`) —
  нормализован до `TS-1002` и успешно сверен.

  «отменён», остаток не расходует.
